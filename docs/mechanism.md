# 实现机制

PP3 Toolkit 的抽象不是对 PP3 的另一套语法，而是把重复出现的 DSL 路由模式命名、组合，再在编译期静态展开。本包不截获 Runtime 执行，不把运行时整数取回 Python。

## PP3 的图视角

运行内存可看成有向图：每个内存地址是一个节点，保存整数值；当前 `view` 决定后续 `~depth`、`^depth`、`*depth` 沿图走几条边。`~d` 读取最终节点，`^d` 写入最终节点，`*d` 交换 view 与最终节点。地址 0 在常用宏中充当稳定路由锚点。

直接寻址固定指定地址；本工具箱构造的宏只用立即数设置 view，再通过间接寻址追踪路径。最简单的自然数槽读取是 `&slot ~1`：令 view 为地址，再读它的一条边。标量写入和引用写入需要不同深度，因为标量可沿正地址的自环/标记回到零锚点，而零头引用本身就是负地址。把引用当普通自然数写入会多走路由边，导致目标错位或覆盖标记。

局部标记使宏能在不枚举输入值的情况下做一些全局工作。例如判等把一个地址临时标成“已占用”，探测另一个数值对应地址后再恢复旧标记。关键不只是找到答案，还要把被借用的图结构恢复到原状态，避免后续宏读取到污染标记。

更完整的底层图模型、正地址标记和链表路由实验见 [PP3-Lab 的图模型](https://github.com/JDK8u341/PP3-Lab/blob/main/docs/01-graph-model.md)、[局部地址标记](https://github.com/JDK8u341/PP3-Lab/blob/main/docs/02-address-marking.md)与[零头记录](https://github.com/JDK8u341/PP3-Lab/blob/main/docs/07-linked-records.md)。这里保留实现概要，链接作为更深层推导与测试记录。

## 两遍槽位规划

`Macros.slot(name)` 为静态控制值分配负地址槽，-1 和 -2 留作路由标记。数组与堆需要一片独立的动态地址区；若在生成器开始时猜测起点，后续宏新申请的槽可能与输入长度无关地碰撞。

`compile_program(generator)` 因此运行生成器两遍：

1. 预览展开并收集全部具名槽。
2. 以“槽数量 + 两个标记 + 安全间隔”为动态区边界重新展开。
3. 比较两次槽名到地址的映射；生成器若不确定性地申请不同槽则立即报错。

两遍只执行 Python 的模板构造逻辑，不读取运行时输入。生成器应是确定性的，且调用顺序不能依赖运行值。

## 自然数宏与符号/幅值

普通数据槽只保存非负数。任意有符号整数被拆成 `(magnitude, sign)`：`magnitude >= 0`、`sign` 为 0/1，零的符号规范化为 0。`decode_integer` 用两个方向的图探测解析标准整数输入，在有限个临时地址碰撞点恢复原幅值；它没有扫描整个负地址保留区。

`equal` 使用局部地址标记，工作量不按差值递减；`compare` 先判等，非等时才复制并同步减小两个操作数，因此非等路径成本与较小幅值有关。`add_into`、`subtract_from`、`divmod_unsigned` 和十进制格式化是透明的重复加减/除法模板，工作量依然可能与数值幅值成正比。通用并不代表常数时间，也不等于机器整数性能。

宏包含重要前置条件：例如 `divmod_unsigned` 分母必须大于零，`subtract_from` 目标不得小于来源；槽不能与宏内部 scratch 槽冲突。scratch 槽按名称复用，同一宏模板的嵌套重入需要额外证明。详见[API 参考](api.md)。

## 负地址数组

`NegativeArray` 的第一个元素放在静态槽下方，后续元素地址依次减一。游标保存在单独槽中，`advance` 只移动游标，`read`/`put` 访问当前位置。元素零值合法，所以数组遍历必须依据显式长度，而不能把零当结束标记。

数组指针与载荷选择不同路由深度。写入表达式不能读取将要写入的目标旧值，因为路由先把地址节点临时改成自环；若想原位更新，应使用 `change`。同一 `Macros` 下创建的多个 `NegativeArray` 默认共享动态起点，不能假设它们天然拥有互不重叠的空间；多结构共存通常应使用同一个 `Arena`。

## 零头记录与引用

记录以永久零头开始：零头地址总保存 0，字段依次放在其下方。独立零头提供节点身份，因此相同载荷、载荷为零、负地址值或重复记录都不会混淆。记录中的字段可存自然数，也可存指向另一个零头的引用，但必须通过对应的载荷/引用 API 写入。

`RecordHeap` 是 `[head=0, magnitude, sign, next]` 的四格便捷布局。`Arena(width)` 是可配置字段数的通用布局，按 `width+1` 格前进。分配假设新地址尚未写入，利用 PP3 隐式零内存，不逐字段清零。

`RecordList` 显式维护 head/tail，节点有所有权约束：追加把节点转入一条链；弹出先断开 NEXT 后可转移；拼接只在同堆、节点集合不相交时转移来源链所有权。稳定归并排序反复拆分并拼接节点，重复键取左段，因此不需要遍历值域或建立字节桶。比较算法的成本仍受数值幅值影响。

## 指令机器与双帧

`InstructionMachine` 使用共享 Arena 节点保存 opcode、参数、括号配对、临时括号栈前驱和线性后继。加载时的括号边与运行时的 PC 后继是两种独立关系：程序可沿后继正常前进，也可从括号节点直接跳到配对节点之后。`run` 只生成取指循环；调用者传入 dispatch DSL 决定每个 opcode 的意义。

`dual_frame` 先用两次 `@input` 读源码和数据长度，再从 Runtime 的行字符缓冲连续消费两个定长帧。中间不隐含分隔符，合成的 LF 和 NUL 都是普通字符。帧内码点受限为 0..255。加载错误会抑制解析/执行回调，但仍消费已声明的剩余字符，以保持后续缓冲边界；真正的提前 EOF 和整数解析错误不被吞掉。

此工具不替用户定义 guest 语言的 EOF、回绕、非法代码或终止语义。那些是题面/解释器自身的设计决策，必须显式写进使用方文档。

## 实际验证与参考

本仓库测试把生成源码交给固定版本 PP3 的 `IRBuilder(op_map=std_register)`，并在 `Runtime(can_direct_addressing=False)` 下执行，覆盖算术、数组、排序、帧、括号机器与循环。

PP3-Lab 保存更底层的性质、反例与测量方法：[比较与排序](https://github.com/JDK8u341/PP3-Lab/blob/main/docs/03-comparison.md)、[验证与成本模型](https://github.com/JDK8u341/PP3-Lab/blob/main/docs/06-validation.md)。Lab 中某个技巧的可观察计数仅适用于其给定输入族，不能直接推广为每个宏调用的精确性能公式。
